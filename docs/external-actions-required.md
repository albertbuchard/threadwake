# External actions still required

## What is already complete

The public local-evaluation package has a reviewed 132-file allowlist, Apache License 2.0, public privacy, terms, support, and security routes, publisher metadata for Albert Buchard, synthetic fixtures, generated dependency notices, and a GitHub Actions workflow. The package validator passes 76 tests. The implementation suites pass 15 application files with 167 tests and 6 contracts and MCP files with 31 tests: 21 files and 198 implementation tests in one receipt.

The local plugin contains one skill and exactly 8 deterministic fixture tools. Its bundled executable and notices are reproduced from pinned dependencies, and installed-cache execution has passed while source-repository reads were denied. These facts support a public source release. They do not turn Threadwake into a hosted service or a plugin-directory listing.

## Evidence limitations that remain explicit

- True browser 200% zoom is unproved. The available text-scale fixture is not described as browser zoom.
- Formal Chrome DevTools and Core Web Vitals measurements are unavailable in the current evidence.
- The previously known Sites project returns `project_not_found`. No duplicate project or replacement deployment is claimed.
- The standalone application and MCP fixture remain separate; no application adapter connects them.
- There is no hosted endpoint, production authentication, multitenancy, telemetry service, or live Forge access.

These limitations do not block publication of the local-evaluation source. They do block stronger claims that depend on the missing evidence or capability.

## Before an MCP Apps visual wrapper

- Receive a separately reviewed public-safe visual shell or component identity.
- Import only released public-safe contracts and components.
- Implement a thin, read-only wrapper without modifying signed Codex application bundles.
- Keep real host task, turn, item, and message identifiers and excerpts out of public fixtures.

The current plugin has no `.app.json` and no MCP Apps widget.

## Before live Forge-backed operation

- Obtain explicit authority for the exact Forge integration and data scope.
- Freeze the supported identity, hierarchy, lifecycle, outcome, evidence, pagination, permission, conflict, idempotency, and rollback mappings.
- Define a server-side credential store and least-privilege scopes.
- Complete cross-tenant, prompt-injection, stale-version, offline, and partial-failure tests.
- Define logging, redaction, retention, deletion, incident response, and support.
- Run separate live-read and live-write safety reviews before enabling either capability.

Live Forge access is not part of this release.

## Before a hosted MCP service

- Select and authorize a production host and domain.
- Deploy one stable public HTTPS Streamable HTTP endpoint, normally ending in `/mcp`.
- Implement production authentication and authorization for user-specific data.
- Define tenant isolation, availability, rate limits, monitoring, redaction, retention, deletion, and incident response.
- Update the public policy pages to match the observed hosted data handling.
- Complete domain verification through the submission portal.
- Prepare reviewer-ready accounts or synthetic fixtures that do not require private-network access, email or SMS confirmation, or an unexpected multifactor prompt during review.

OpenAI's [MCP server guide](https://developers.openai.com/plugins/build/mcp-server) requires a stable public HTTPS Streamable HTTP endpoint for public submission. A local server or development tunnel does not satisfy that requirement.

## Before public plugin-directory submission

- Choose the correct verified developer or business identity in the OpenAI Platform.
- Confirm that the submitter has Apps Management write permission for the publishing organization.
- Supply the stable public production MCP endpoint and any required authentication.
- Freeze the skill bundle, tool schemas, tool annotations, starter prompts, listing copy, assets, regions, and release notes.
- Ensure the verified publisher identity matches the website, support, privacy, and terms routes.
- Confirm accurate `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` values for every tool.
- Run at least five positive and three negative deterministic cases against the final product.
- Provide working reviewer access when authentication is required.
- Resolve portal validation findings, review the final draft, and submit through the official portal.

The current [OpenAI submission guide](https://developers.openai.com/plugins/deploy/submission) describes these prerequisites. Threadwake has not been submitted, reviewed, or approved by OpenAI.

## Future decisions

The publisher may later decide whether to pursue a hosted MCP service, a thin read-only MCP Apps wrapper after its public-safe dependency is released, live Forge integration, or OpenAI directory submission. Each is a separate scope with its own safety, privacy, infrastructure, and authorization requirements. None is implied by this public source release.
